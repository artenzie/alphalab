## Phase 1 started early: SQLite schema (Mon 16 Nov plan item)

**What we built.** One database, `data/alphalab.db` (gitignored), created from `data/schema.sql` by `data/db.py` (`python -m data.db`). No trading logic yet. 33 tests in `tests/test_schema.py`, all passing.

| Table | One row per |
|---|---|
| `agents` | Agent: 1–15 (`us_equity`) and C0, C1 (`crypto`), with kind, risk profile and mirror account. The only editable table |
| `prices` | Daily bar *per fetch*: raw and split-adjusted OHLCV, `fetched_at` |
| `snapshots` | Asset class per day: `cutoff_ts`, payload, SHA-256 hash, data checks |
| `decisions` | Agent per decision attempt: model, provider that served it, reasoning setting, prompt hash, raw response, parsed targets, reasons, tokens, cost, latency, status |
| `risk_events` | Clip, rejection or forced reduction |
| `orders` / `fills` | Order (written once), then its fill or cancellation, with price, slippage and fees |
| `positions` / `equity` | Agent per day (crypto per calendar day) |
| `mirror_recon` | Mirrored agent per day: ledger vs Alpaca |
| `heartbeat` | Run event: started, finished, error |

**Why append-only.** The log is the evidence. If any row can be quietly changed, there's no way to prove afterwards that a result wasn't tuned after we saw it, the same reason scientists write in pen in a lab notebook. So every data table has SQLite triggers that abort any `UPDATE` or `DELETE`. A mistake gets fixed by adding a new row whose `corrects_id` points at the wrong one, so both the error and the fix stay visible. This shapes the design: an order never changes from "pending" to "filled"; instead it's pending until a row appears in `fills`. The heartbeat writes a "started" row and a "finished" row rather than updating one. The triggers stop accidents, not a determined person (anyone can drop a trigger), which is why the nightly off-device backup still matters.

**Why prices are versioned.** When a stock splits, every old price gets re-adjusted. Overwriting them would mean a snapshot rebuilt later wouldn't match the one the agents actually saw. So each fetch adds new rows, and `db.prices_as_of(cutoff)` returns, for each bar, the latest version fetched at or before the cutoff. Prices become point-in-time: a later re-adjustment is invisible to an earlier snapshot. Raw prices are kept too, so adjustments can be checked.

**Other guards built into the schema:**
- **No future data (rule 1):** a decision can't be timestamped before its snapshot's `cutoff_ts`, and a crypto agent can't use an equity snapshot.
- **UTC everywhere:** every timestamp must look exactly like `2026-11-16T22:45:00.123Z`. One fixed format means sorting the text also sorts by time.
- **Status is restricted:** only `ok`, `invalid`, `unavailable` or `capped` are allowed.

**Definition worth remembering.** `cutoff_ts` is the *knowledge time*, the moment the snapshot is built, not the 16:00 market close. If it were the close, the day's own bars (fetched at 17:30) would count as "not yet known".

**Next:** the price fetcher. Alpaca daily bars are stamped with their *start* time, so the snapshot builder must also check a bar is complete (the day has closed) before using it. This matters most for crypto, where the "day" ends at 00:00 UTC.

**How it works:**

- **Equities are fetched twice**, raw and split-adjusted, then merged into one row per bar (`open..volume` and `adj_*`). If the two fetches cover different days, that's an error, not a silent gap.
- **Versioning.** A bar gets a new row only if some value differs from its latest stored version. Re-running inserts nothing; a later split re-adjustment adds a new version, which `prices_as_of` hides from earlier snapshots.
- **No unclosed bars (rule 1).** An equity bar for day D is stored only after 16:00 ET on D. A crypto bar is stored only once its 24 hours have passed. Alpaca returns today's partial crypto bar, so this guard matters in practice.

- **Heartbeat.** `started`, then `finished` with per-symbol counts (fetched / inserted / unchanged / rejected), or `error`.

**Crypto day boundary checked.** Alpaca's daily crypto bars start at exactly 00:00 UTC, so they match §13 and are used directly. The fallback (building days from 24 hourly bars) wasn't needed. As a guard, any crypto daily bar not stamped 00:00Z stops the run. Equity daily bars are stamped 05:00Z (midnight ET), so the bar date is taken in New York time.

**How it works:**
- **Chunks by calendar year.** 2024-11-01→12-31, 2025, 2026→now. Each chunk ends 1 s before the next starts, so none overlap. Each chunk takes 3 calls (stock raw, stock split, crypto), with a 1 s pause between chunks: about 9 calls in total, far below Alpaca's 200/min.
- **One transaction and one `fetched_at` per chunk.** If a later chunk fails, the earlier ones stay stored, the `error` heartbeat records how many chunks were stored, and a re-run inserts nothing for them.
- **Coverage report after every run** (both modes), printed and saved in the `finished` heartbeat. For each symbol: first date, last date, bars, expected bars, late start, gaps. Equities are expected on every NYSE session from Alpaca's trading calendar whose 16:00 ET close has passed. Crypto is expected on every calendar day whose 00:00 UTC bar has closed. Gaps are listed, **never filled**. Bars on unexpected days are listed too.

**Real run** (Sat 14 Nov, `--start 2024-11-01`): 15,450 bars fetched, 15,305 inserted. The 140 unchanged bars were 9–13 Nov from the first run; the 5 rejected were today's unfinished crypto bars. A second run inserted 0.

|---|---|---|---|---|---|---|

| 5 crypto pairs | 2024-11-01 | 2026-11-13 | 743 | 743 calendar days | none | none |

**Caveat: IEX volume is IEX's share only.** We use the free IEX feed, so each bar's `volume` (and `trade_count`, `vwap`) covers only trades on IEX, a few percent of consolidated US volume, not the whole market. Prices track the market closely, but volume does not:
- Absolute volume is understated by an order of magnitude and can't be compared with published (SIP) volume figures.
- Ratios against the stock's own history, like §4's "volume relative to its 20-day average", stay internally consistent but measure *IEX activity*. IEX's market share drifts and varies by stock, so the ratio is noisier than on full-market data and can move without any change in total market volume.
- Any volume-based indicator (relative volume, OBV, volume-weighted signals) inherits this. Every agent sees the same data, so the comparison between agents stays fair, but results that depend on volume should say so in the paper.

## Phase 1: market calendar (Thu 19 Nov plan item, done early)

**What we built.** `data/calendar.py`, which the scheduler will call: `is_trading_day(d)`, `session_close(d)`, `equity_times(d)` (`bars_fetch_at` / `snapshot_at` / `decide_at` = close + 1:30 / 1:45 / 2:00, protocol §3) and `crypto_times(bar_date)` (§13). Every time comes back as UTC. ET and UK times are converted with the `America/New_York` and `Europe/London` tz zones, never with fixed offsets. 41 new tests in `tests/test_calendar.py`, using a fake Alpaca client, so no network; 107 pass in total.

**How it works:**
- **Cache in the database, append-only.** There are two new tables. `calendar_fetches` records each fetch and the date range it asked about. `market_sessions` stores that fetch's sessions, with open and close in UTC. For a date D, the newest fetch whose range contains D answers: a row means open, no row means closed. The range matters because Alpaca lists trading days only, so a weekend or holiday is "a covered date with no row". A closure announced late (like the Carter day of mourning, 9 Jan 2025) shows up as a newer fetch without that day, and nothing is edited. A refresh that changes nothing stores nothing.
- **Network blips.** Lookups read only the cache, which covers 2024-11-01 to 2027-12-31, so the whole experiment is covered. The network is touched by `refresh()` (the daily job, using the same retries as ingest) and, once, on a date no fetch covers. If neither works, it raises `CalendarUnavailable` and never guesses.
- **Early closes** come straight from Alpaca. On those days the schedule shifts the same way, e.g. Fri 27 Nov 2026 closes at 13:00 ET, so bars at 14:30, snapshot at 14:45 and decide at 15:00 ET.
- **Crypto** (protocol v1.1, §13): fetch at 00:05Z, snapshot at 00:10Z, decide at 00:15Z after each 00:00Z daily bar close, every day. These are pure UTC, so clock changes never move them.

**First real fetch** (Sat 14 Nov, 22:12 UTC): 793 sessions from 2024-11-01 to 2027-12-31. 2024-11-01 to 2026-11-13 holds 510 sessions, which matches the backfill's expected count exactly. The official run (11 Jan to 2 Apr 2027) has **57 trading days**. Good Friday falls on 26 Mar 2027, inside the run. The early closes are all present: the day after Thanksgiving and 24 Dec at 13:00 ET, and 3 Jul 2025 at 13:00 ET. A second refresh stored nothing.

**When the decision runs, in UK time.** The market closes at 16:00 ET and agents decide two hours later, at 18:00 ET:

| When | Decision (UK) | Why |
|---|---|---|
| Most days | **23:00** | Both countries on standard time, or both on summer time: always 5 h apart |
| Clock-change weeks | **22:00** | Only one country has switched, so the gap is 4 h |
| Fri 27 Nov 2026 (early close 13:00 ET) | **20:00** | Close 18:00 UTC + 2 h |

The clock-change weeks: in autumn the UK switches first (2026: 25 Oct, US 1 Nov), so it's one week. In spring the US switches first (2027: 14 Mar, UK 28 Mar), so it's two weeks, **15–25 Mar 2027, inside the official run**. In UTC the decision time moves too: 23:00Z in winter, 22:00Z in US summer time. That's why the scheduler must work in UTC from the calendar, not from a fixed UK time. 24 Dec 2026 (shakedown) is also an early close, with the decision at 20:00 UK.

## Phase 1: the no-future-data snapshot (Sat 21 Nov plan item, done early)

**What we built.** `data/snapshot.py`. `build_snapshot(conn, asset_class, decision_date, mode)` is the one function every agent's market data comes through (protocol §4, CLAUDE.md rule 1). It covers all 23 equity symbols or the 5 coins (§13). `store_snapshot()` writes a live snapshot to `snapshots` with its canonical JSON, sha256, `cutoff_ts` and the data-check results (run as of the cutoff, so they see exactly what the snapshot sees). 30 new tests; 185 pass in total.

**The cutoff** is the protocol's snapshot time: session close + 1:45 for equities (§3, so 14:45 ET on early-close days) and 00:10Z on D+1 for crypto (§13). A bar gets in only if it passes **every** guard, and each guard is enforced on its own:

| Guard | Rule |
|---|---|
| Date | `bar_date <= D` |
| Closed | equities: the session's real close (cached calendar) is at or before the cutoff; crypto: `bar_ts + 24h <= cutoff` |
| Known | live mode only: the latest version with `fetched_at <= cutoff` (`db.prices_as_of`) |

**Fields** (split-adjusted closes and volumes; `null` when history is too short):

| Field | Definition |
|---|---|
| `last_close`, `closes_20`, `dates_20` | latest close; last 20, oldest first |
| `ret_1/5/21/63` | `c[t] / c[t-N] - 1`, N bars back |
| `ma_20`, `ma_100` | simple means |
| `vol_20` | sample std (ddof=1) of the last 20 daily simple returns × √252 (equity) or × √365 (crypto, trades every day) |
| `z_20` | `(c[t] - ma_20) / sample std of the last 20 closes` |
| `volume_ratio_20` | today's volume / mean of the last 20 volumes, today included |

Computed in plain Python with `math.fsum` (no pandas), so the floats, and therefore the hash, don't depend on library versions. On the real data every field matched an independent pandas calculation.

**History for rule-based agents.** `snap.history(symbol, n)` returns up to 252 adjusted bars as immutable tuples. They come from the rows loaded at build time, under the same guards; the snapshot object holds no database connection. Storing 252 bars × 23 symbols every day would be ~500 KB, so the payload carries `history_sha256` instead: the snapshot's hash covers what the rule-based agents see, and the history can be rebuilt and checked.

**Hash.** Canonical JSON (sorted keys, no spaces, NaN refused), sha256 of its UTF-8 bytes. The payload has no build time, so the same inputs always give the same hash (tested, including rows inserted in reverse order).

**Live vs backtest, and the backtest's limitation.** Every price row in the database was fetched on Sat 14 Nov 2026, 21:50–21:59Z: the backfill. A live snapshot for any earlier date therefore sees nothing, because nothing was known at its cutoff. Backtest mode drops the `fetched_at` guard (the other two stay) and takes the latest stored version of each bar. **That makes a backtest snapshot a reconstruction, not a point-in-time view.** It uses today's version of each past bar and today's split adjustment, including any correction Alpaca made after the date. For our window that is harmless (no splits; checks clean), but it isn't the same guarantee. Backtest snapshots carry `mode: "backtest"` in the payload (so it's part of the hash), refuse dates whose cutoff hasn't happened yet, and `store_snapshot` refuses them. A backtest snapshot can never be confused with a live one.

**Tests: proving it can't see tomorrow.**
1. A bar dated D+1 at a price of 10⁹, with one version fetched *before* D's cutoff, leaves the snapshot byte-identical in both modes. For crypto that bar starts at 00:00Z D+1, before the 00:10Z cutoff, so only the date and closed-bar guards keep it out.
2. A version of bar D fetched 1 ms after the cutoff is ignored in live mode; one fetched 1 ms before is used. Backtest mode does pick up the late one, which is the limitation above, now pinned down by a test.
3. Unclosed bars: on Fri 27 Nov (13:00 ET close) the bar is rejected at 12:59:59.999 ET and accepted at 13:00; on a normal day, rejected until 16:00 ET even when it was "fetched" mid-session. A crypto bar is rejected until bar_ts + 24h.
4. Replay: for 20 random past dates (fixed seed), the snapshot from the full database has the same hash as one from a copy with everything after the date deleted (and in live mode, everything fetched after the cutoff). Runs on the synthetic data in both modes and on a copy of the real database in backtest mode (the real file is only opened read-only).
5. Indicators against hand calculations: closes 100…200 (e.g. `ma_20` = 190.5, `z_20` = 9.5/√35, volume ratio 3000/1100), alternating ±10% returns for `vol_20` (√(0.2/19)·√252), nulls on short history, split-adjusted prices used across a 10:1 split.
6. Hash deterministic, changes when any history bar changes (even one too old to touch a 20/100-day field), and differs between modes.

## Phase 2: agents 1 and 2 (Mon 23 Nov plan item, done early)

**The interface (`strategies/base.py`).** Every agent, rule-based now and AI later, is one function: `decide(snapshot, portfolio, context) -> Decision`.
- `Decision`: target weights per symbol (fraction of portfolio value, negative = short), or `weights=None` for "hold, no change", plus a one-line reason. Weights must be finite numbers. The reason must be non-empty and one line. Both are frozen.
- `Portfolio`: the agent's own cash, shares per symbol and value, read-only. Minimal until the ledger exists.
- `Context`: `is_first_day_of_run`, `is_first_session_of_week`, `is_first_session_of_month`. The runner computes it with `build_context(decision_date, run_sessions)` from the calendar's session list, never the agent. Week = ISO week of the previous session; month = calendar month of the previous session. So Tue 19 Jan (after MLK Day) starts a week, and so does Mon 4 Jan 2027 after Thu 31 Dec.

## Agent 4 capacity and no resizing (protocol v1.4)

**Artem's decision, written into the protocol as its own commit first.**
- **§5, agent 4:**
  - At most 10 open positions (10 × 10% = 100% gross), at most 3 of them short (30%).
  - Exits free their slots first. Entry signals then fill the free slots, largest |z_20| first, ties A→Z. The rest are skipped.
  - An entry gets 10% of current portfolio value.
  - **No resizing:** open positions keep the weight they have drifted to until they exit, so orders come only from entries and exits. This replaces the v1.3 "keep their 10% target".
- **§6:** a breached limit is fixed by scaling the breached side down pro rata, and every clip is logged.

**How "no resizing" fits the target-weight interface.** For an open position that isn't exiting, the agent outputs its current weight, shares × snapshot close ÷ portfolio value. Converted back with the same close and value, that gives exactly the shares it already holds, so no order. **Requirement for the ledger (Phase 3):** size orders from the decision snapshot's close and the portfolio value used in the decision, and treat a share change below a small tolerance as no order. Otherwise, rounding or sizing at the next open would create the tiny resizes v1.4 rules out.

**Interpretation choices** (in the code and tests; tell me if any is wrong):
- Long and short signals compete for the same slots on one |z| ranking. A short signal with no short slot left is skipped, and the next signal is tried, so a long can still get in.
- A long that exits at z ≥ +1.5 counts as flat and can flip to a short if a slot is free. Same for a short at z ≤ −1.5.
- In §6, "the breached side" means: the per-stock limit cuts that one position, the total-short limit scales all shorts, and the gross limit scales all positions.

**Tests.** The agent 4 section was rewritten (13 tests). It covers the thresholds, exits, no resizing (a 12% long and an −8% short stay at 12% and −8%, and convert back to exactly the shares held), capacity (14 signals → the 10 most extreme, the skipped ones named in the reason), slots counted with open positions, exits freeing slots, a full book with a strong signal → hold, |z| ties broken by symbol across long and short, the short cap (with and without open shorts), missing z, and a stray SPY being closed. ## Risk checks (Phase 2, planned for Sun 29 Nov)

**What was built.**
- `execution/risk.py`, a set of pure functions: no database, network, file or environment access. A test checks this by blocking all of them.
- `apply_risk(agent_id, decision, etb_flags, current_weights) -> (weights, events)`.
  - Profiles come from the §6 table, plus §13 for crypto: C1 is long only with at most 50% per coin, and C0 is long only up to 100%.
  - Checks run in this order: shorts not allowed for this agent → short in a stock that isn't easy-to-borrow → per-stock cap → total-short cap (all shorts scaled pro rata) → gross cap (everything scaled pro rata).
  - A hold passes through untouched.
  - Each step only zeroes, cuts or scales by a factor ≤ 1. An assert checks that no output weight is larger in size than its input or has flipped sign.
- `margin_check(equity, gross_exposure, positions)`.
  - Triggers when equity is below 30% of gross. It then scales every position by equity / (0.40 × gross), so equity ends at exactly 40% of the new gross.
  - Equity ≤ 0 closes everything.
  - The 30% boundary is compared as a ratio with a 1e-9 tolerance, because 0.30 × 100 is 30.000000000000004 in floats and would otherwise make exactly 30% trigger.
- **Events.** There is one event per affected symbol. Its keys are the exact `risk_events` columns: `event_type` (clip / reject / forced_reduction), `rule`, `symbol`, `requested_weight`, `applied_weight`, and `detail` (a JSON string with the limit, the measured value and the factor). A test inserts them into the real schema.
- **Limit tolerance.** Limits are compared with a 1e-9 tolerance, so 5 × 30% for agent 15 (which floats to 1.5000000000000002) is allowed and 151% is clipped.

**Artem's decisions on the plan.**
1. **Easy-to-borrow only blocks opening or increasing a short.** That's why `current_weights` is the 4th argument.
   - A new short (or a flip from long) in a stock that isn't easy-to-borrow → 0.
   - A short larger than the one held → kept at its current size.
   - An existing short whose stock is no longer easy-to-borrow is kept. Closing it would be a trade the agent didn't ask for (§6).
2. A symbol missing from `etb_flags` counts as not easy-to-borrow.
3. Drift is only checked on decision days. Margin runs every day.
4. Equity ≤ 0 closes everything.

**Tests.** `tests/test_risk.py` has 85 tests. They cover:
